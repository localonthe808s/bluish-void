## 2. The trail: the CDN serves day files frozen at about 07:00 ET (fixed on this branch)

Without a query string, `cdn.bluishvoid.com/kalshi/trail/ny_high_<date>.jsonl` returns whatever copy the Cloudflare
edge cached first. It holds that copy for days, ignoring the object's `cache-control: max-age=120`:

| day | plain URL (cached) | age | bucket (cache-busted) |
|---|---|---|---|
| 10-22 | 288 rows, to 23:55 | 42 s | 288 |
| 10-23 | to 23:55 | 43 s | 263 |
| 10-24 | 83 rows, to 07:00 | 428,314 s (5 days) | 285 |
| 10-25 | 71 rows, to 06:00 | 345,688 s | 281 |
| 10-26 | 73 rows, to 06:05 | 259,107 s | 288 |
| 10-27 | 80 rows, to 07:00 | 169,216 s | 283 |
| 10-28 | 85 rows, to 07:00 (107,644 B) | 82,749 s | 290 (366,475 B) |

The bake writes every row and the R2 append works. Only the edge copy is stale. Whatever first fetches a day's
file at 06:00-07:00 ET while the day is still running freezes it there. The 10:00Z review routine's own step-2
fetch is the likely culprit: 10-25 and 10-26 were cached at 10:01Z and 10:06Z. This run fetched
`ny_high_2026-10-29.jsonl` at about 10:05Z, so today's plain URL is now frozen at 06:00 too. The edge TTL override
is a Cloudflare setting outside the repo. Purging `kalshi/trail/*` or honouring origin cache-control there is the
owner's call. The review procedure should fetch with `?v=<date>` like trail_study.py does. I made that change for
the sheet, not the README.
