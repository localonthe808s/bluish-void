## Findings

**A. CDN edge serves stale trail objects; insider_study read truncated days (medium, fixed).**
Requests without a query string get an edge HIT with `age: 86388` despite `max-age=120`. ny_high_2026-10-29.jsonl
came back as 73 rows ending at 06:00 ET (last-modified 10-29 10:02Z). The origin object has 290 rows ending at 23:55
(last-modified 10-30 03:56Z). Same pattern, plain request against fresh copy:

| day | plain request | fresh copy | TWC rises missed |
|---|---|---|---|
| 10-24 | 83 rows | 285 rows | 6 |
| 10-26 | 73 rows | 288 rows | 6 |
| 10-27 | 80 rows | 283 rows | 0 |
| 10-28 | 85 rows | 290 rows | 5 |

`insider_study.py:200` fetched the trail with no buster. For settled days it also stores the result permanently in
`insider_cache`, which actions/cache restores every night, so the short copies never refresh.

Fix: add `?v=<unix time>` to the URL, and rename the cache key from `trail_` to `trail2_` so the truncated entries are
fetched again once.

Before/after, running `twc_bumps('ny_high', 10-24, 10-29)` with an empty cache: **5 windows before, 28 after**.
The 23 added windows are TWC rises from the afternoon trail rows.

**B. Same exposure, not fixed.**
- `kalshi_daily.py:3698` `trail_rows()` fetches the trail with no buster. It only feeds execution_score (fills
  against plan), so fills after about 07:00 ET would match no bake row.
- The plain `kalshi/live/kalshi_ny.json` served `updated 2026-10-25T06:00 ET`, five days stale. The page itself always
  adds `?v=`, so the sheet is fine.

The root cause is likely a Cloudflare cache rule that overrides the origin TTL. That is for the owner to check; I did
not change it.

**C. NY high: errors below the actual 11 of 12 days (medium, not fixed).** Numbers are in section 1. The value is
learned; no hand tuning.

**D. Notes.** The README still lists las/aus. The nightly refit starts about 7 hours late. hmax steps down to whole
numbers in the trail. The kernel is off by a 0.0048 gain against a 0.01 bar.
